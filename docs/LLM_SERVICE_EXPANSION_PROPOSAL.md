# AI 기본법 RAG 서비스 기능 확장 기획서

- 작성일: 2026-10-18
- 대상: 현재 AI 기본법 근거 기반 QA 프로젝트
- 목적: LLM 기능, 문서·이미지 처리, RAG·Tool Calling, 검증·복구, 평가·운영 분석, 테스트·문서화 요구사항을 실제 구현과 검증 자료로 충족한다.
- 문서 상태: 추가 구현을 위한 기획. 아래 제안 기능을 현재 구현 완료 기능으로 간주하지 않는다.

## 1. 서비스 개요

사용자가 자연어 질문 또는 법령 문서·이미지를 입력하면 핵심 정보를 추출하고 질문 의도를 분류한다. 필요한 검색·조문 조회 도구를 LLM이 선택해 실행하고, 확인된 근거를 바탕으로 설명과 요약을 생성한다. 응답은 구조 및 인용 검증을 거치며, 근거가 부족하면 추가 질문 또는 답변 보류로 처리한다.

핵심 사용자 시나리오:

1. “제33조 내용을 알려줘” → 조문 번호 추출 → 조문 조회 도구 → 원문과 쉬운 설명.
2. “고영향 AI 사업자의 의무를 정리해줘” → 의무·목록형 분류 → 관련 법령 검색 → 조문별 의무 요약.
3. 법령 PDF 업로드 → 텍스트·조문 구조 추출 → 문서 요약과 근거 기반 질문 응답.
4. 스캔 이미지 업로드 → OCR → 인식 결과 확인 → 구조화·요약·질문 응답.
5. 범위 밖 또는 식별 불가능한 입력 → 누락 사유와 보완 방법 안내.

## 3. 선행 개선: 실제 LangGraph 실행과 데이터 흐름

현재 `LangGraphRAG.answer()`는 컴파일된 그래프를 실행하지 않고 직접 분류·검색·답변을 호출한다. 컴파일된 그래프에는 분류와 생성만 포함되어 있다. 따라서 실제 API 경로를 그래프 실행으로 연결하는 것을 첫 작업으로 진행한다.

추가로 현재 다음 한계를 개선한다.

- 사전 관련성 검사와 답변 생성에서 검색이 중복될 수 있으므로 검색 결과를 그래프 상태로 전달한다.
- 원본 질문과 검색용 재작성 질문을 분리한다. 답변 생성·캐시 식별에는 원래 요청의 의미를 보존한다.
- 현재 관련성 평가는 어휘 겹침 휴리스틱이다. LLM 관련성 평가를 추가하고 평가 데이터로 유효성을 비교한다.
- 현재 답변 검사는 출처 표기 존재 여부 수준이다. 인용 ID 유효성과 주장별 근거 여부를 추가 검증한다.
- 캐시 조회를 검색보다 먼저 수행하고, 검증된 최종 답변만 저장한다.
- 새로고침은 캐시만 우회하며 품질 검증·재시도를 생략하지 않도록 한다.
- 비동기 실행 지연 문제를 최소 재현과 시간 제한 테스트로 조사하고, 실제 그래프 실행 완료를 통합 테스트로 확인한다.

목표 흐름:

```text
질문 또는 업로드 문서
  → 입력 검사·문서 추출·OCR
  → 요청 범위에 맞는 캐시 조회
  → LLM 정보 추출·의도 분류
  → LLM 도구 선택 → 인자 검증 → 도구 실행 → 결과 반환
  → 근거 관련성 평가
      ├─ 부족: 질의 재작성 후 제한된 재검색
      └─ 충분: 답변 또는 요약 생성
  → 구조·필수값·인용·근거 검증
      ├─ 실패: 제한된 수정·재생성
      └─ 통과: 캐시 저장·응답
  → 요청 단위 시간·오류·모델 사용량 기록
```

## 4. 기능 상세

### 4.1 LLM 정보 추출·의도 분류

질문에서 `intent`, `law_name`, `article_number`, `keywords`, `target`, `missing_fields`를 추출한다. 의도는 `definition`, `article_lookup`, `obligation`, `comparison`, `summary`, `out_of_scope`, `clarification`으로 시작한다.

```json
{
  "intent": "article_lookup",
  "law_name": "인공지능기본법",
  "article_number": 33,
  "keywords": ["고영향 인공지능"],
  "target": null,
  "missing_fields": []
}
```

문서에서는 법령명·조문·의무 주체·의무 내용·예외·시행일을 추출하고 각 필드에 원문 위치를 연결한다. 원문에 없는 값은 `null`로 반환한다. 모호한 질문은 추가 질문으로 처리하며 모델이 반환한 자신감 수치를 정확도로 간주하지 않는다.

완료 기준: 구조화 결과가 스키마를 통과하고, 필드 추출 F1과 의도 분류 정확도를 고정 평가 세트에서 산출한다. 규칙 기반 분류와 LLM 분류 결과도 비교한다.

### 4.2 문서 요약·답변 생성

조문별 요약과 문서 전체 요약을 제공한다. 전체 요약은 핵심 내용, 적용 대상, 주요 의무, 예외, 확인되지 않은 정보로 구성한다. 모든 핵심 법률 주장에 조문 또는 페이지 인용을 붙인다. 긴 문서는 청크별 요약 후 통합하되 최종 주장과 원문 위치의 연결을 유지한다.

완료 기준: 원문에 있는 조건·예외가 요약에서 누락되는지 평가하고, 존재하지 않는 의무·기한·처벌을 생성하는 오류를 별도 집계한다.

### 4.3 문서·이미지 처리

- 지원 입력: 기존 XML, 텍스트 PDF, 스캔 PDF, PNG, JPEG.
- 텍스트 PDF는 페이지별 텍스트 추출을 우선하고, 텍스트가 없는 페이지는 OCR로 전환한다.
- 이미지·스캔 페이지는 방향 보정·기본 전처리 후 OCR을 수행한다.
- OCR 결과와 페이지 위치를 저장하고 인식이 불확실한 부분을 표시한다. 불확실성 기준은 선택한 OCR 엔진의 출력에 맞춰 정한다.
- 사용자가 OCR 결과를 확인·수정한 뒤 요약·검색에 사용할 수 있도록 한다.
- 업로드 문서는 공식 법령과 출처 유형을 구분한다. 확인되지 않은 업로드 문서를 최신 공식 법령으로 표현하지 않는다.
- 업로드 크기·페이지 수·처리 시간 한도를 설정하고, 요청자·세션별 문서를 분리해 검색한다.
- 문서 내부 지시문은 분석할 데이터로 처리하며 도구 실행 권한으로 사용하지 않는다.

완료 기준: 텍스트 PDF·스캔 PDF·이미지 각각의 성공 시나리오와 손상 파일·빈 파일·인식 실패 처리를 검증한다. 별도 이미지 정답 세트로 문자 오류율(CER)과 핵심 필드 추출 정확도를 측정한다.

### 4.4 RAG 및 Tool Calling

| 도구 | 주요 인자 | 역할 |
|---|---|---|
| `search_law` | `query`, `top_k` | 기존 Hybrid 검색과 조건부 reranking |
| `get_article` | `law_id`, `article_number` | 저장된 조문 정확 조회 |
| `search_document` | `document_id`, `query` | 업로드 문서의 관련 내용 검색 |
| `get_document_section` | `document_id`, `section_id` | 요약·설명에 필요한 원문 조회 |

LLM에 도구 스키마를 제공하고 반환된 도구 이름·인자를 검증한다. 허용된 도구만 실행하며 호출 ID에 맞춰 결과를 모델에 돌려준다. 조회 권한과 문서 범위는 서버에서 적용한다. 도구 실패는 구조화된 오류로 반환하고, 무한 루프를 방지하도록 최대 호출 횟수를 설정한다.

도구 선택 예: “제33조 내용”은 `get_article`, “사업자 의무”는 `search_law`, “올린 문서의 예외 조건”은 `search_document`를 사용한다.

완료 기준: 실제 LLM 도구 호출 3개 시나리오를 기록하고, 올바른 도구·인자 선택률을 평가한다. 일반 함수 직접 호출과 LLM Tool Calling 테스트를 구분한다.

### 4.5 응답 형식 검증·누락 처리·재시도

최종 응답 스키마에 `answer`, `sources`, `status`, `missing_fields`, `request_id`를 정의한다. 상태는 `answered`, `needs_clarification`, `insufficient_evidence`, `failed`로 구분한다. 기존 응답 필드는 유지하고 새 필드는 기본값을 제공해 프론트엔드 호환성을 관리한다.

검증 항목:

- JSON 파싱과 타입·필수 필드·허용 enum 검사.
- 답변의 모든 인용 ID가 실제 반환 출처에 존재하는지 검사.
- 핵심 주장에 인용이 있고, 인용 원문이 주장을 뒷받침하는지 검사.
- 질문의 핵심 요청에 답했는지 검사. 단순 거절 문구 포함 여부로 통과시키지 않는다.
- 추출 누락·OCR 실패·근거 부족·버전 충돌의 이유와 후속 조치를 반환한다.

| 실패 유형 | 복구 정책 |
|---|---|
| 429·일시적 연결 오류·5xx | 전체 시간 예산 내 최대 3회 재시도, backoff·jitter 적용, 가능하면 Retry-After 반영 |
| 잘못된 JSON·필수 필드 누락 | 검증 오류를 전달해 1회 수정 요청 |
| 관련 근거 부족 | 원래 의도를 유지한 질의 재작성 후 1회 재검색 |
| 인용·근거 검증 실패 | 근거와 오류 사유를 전달해 1회 재생성 |
| 필수 사용자 정보 부족 | 추측하지 않고 추가 질문 |
| 영구 오류·재시도 소진 | 명시적 실패 또는 근거 부족 응답, 미검증 답변 캐시 금지 |

각 재시도 한도 외에 요청 전체의 최대 호출 수와 시간 제한을 적용한다. 캐시 키에는 문서 범위·버전·모델·프롬프트·파이프라인 버전을 반영한다.

## 5. 품질·오류·시간·사용량 분석

### 5.1 평가 데이터

기존 `backend/eval/golden_set_v2.jsonl`과 평가 스크립트를 재사용하고 다음 세트를 추가한다.

| 평가 세트 | 권장 초기 규모 | 정답 정보 |
|---|---:|---|
| 의도 분류·정보 추출 | 50문항 | 의도, 법령명, 조문, 핵심 필드 |
| Tool Calling | 30문항 | 허용 도구, 기대 인자, 기대 결과 |
| 문서·이미지 | 20파일 | OCR 원문, 페이지, 핵심 필드 |
| 요약 | 20문항 | 필수 사실, 조건, 예외, 근거 위치 |
| 실패·누락·범위 밖 | 20문항 | 기대 상태, 재시도·보류 여부 |

구현 중 조정하는 개발 세트와 최종 성능을 확인하는 고정 검증 세트를 분리한다. 실험 결과는 측정 전 수치로 채우지 않는다.

### 5.2 변경 전후 비교

1. 현재 코드·설정·데이터를 baseline으로 고정하고 버전을 기록한다.
2. 그래프 실행 정비, LLM 분류, Tool Calling, 검증 루프를 단계적으로 적용한다.
3. 동일 질문·문서·모델·실행 조건에서 baseline과 각 변경을 비교한다.
4. 캐시 hit/miss와 cold/warm 실행을 구분해 시간·사용량을 집계한다.
5. LLM Judge와 원문 기반 사람 검토를 병행하며 실패 사례를 유형별로 정리한다.

주요 지표:

- 검색: Hit@K, Recall@K, MRR.
- 답변·요약: 정확성, 근거 충실성, 핵심 내용·예외 누락률, 환각률.
- 구조화: JSON 유효율, 필수 필드 누락률, 추출 F1.
- 도구: 선택 정확도, 인자 정확도, 실행 성공률.
- 실패 대응: 범위 밖 거절 정확도, 불필요한 거절률, 재시도 복구율.
- 성능: 전체·단계별 응답 시간 p50/p95, 타임아웃률.
- 사용량: 호출 수, 입력·출력 토큰, 캐시 절감량, 요청별 추정 비용.

### 5.3 요청 추적·사용량 저장

PostgreSQL에 `request_runs`, `model_calls`, `tool_calls`, `evaluation_runs` 테이블을 추가한다.

- 요청: request ID, 파이프라인 버전, 상태, 캐시 여부, 시작·종료 시각, 총 소요 시간.
- 모델 호출: 모델명, 목적, 입력·출력 토큰, 지연, 오류, 재시도 번호, 추정 비용.
- 도구 호출: 도구명, 실행 결과 상태, 지연, 오류 코드.
- 평가 실행: 코드·데이터·설정 버전, 문항별 결과, 집계 지표.

추출·분류·생성·검증·재시도·LLM Judge의 사용량을 구분한다. 제공자가 사용량을 반환하지 않으면 `null`과 집계 누락 여부를 기록하고 0으로 처리하지 않는다. 비용은 제공자·모델·가격 기준일을 설정해 추정하며 OCR 등 별도 비용과 구분한다. 민감한 업로드 원문과 도구 인자는 기본 로그에서 제외한다.

## 6. API·프론트엔드·모듈 변경안

아래 경로와 파일은 구현 제안이며 현재 존재하는 것으로 간주하지 않는다.

| 대상 | 변경안 |
|---|---|
| `backend/rag/graph.py` | 실제 async 그래프 실행·분기·재시도·최종 상태 처리 |
| `backend/rag/pipeline.py` | 검색·컨텍스트 구성·생성·캐시 단계를 재사용 가능하게 분리 |
| `backend/rag/schemas.py` | 추출·분류·검증 응답 스키마 |
| `backend/rag/tools.py` | 도구 스키마·실행기·오류 계약 |
| `backend/rag/validators.py` | 인용·필수값·근거·질문 적합성 검사 |
| `backend/documents/` | PDF 추출·OCR·페이지/문서 메타데이터·수명 관리 |
| `backend/common/telemetry.py` | 요청·모델·도구 사용량 기록 |
| `backend/app/main.py` | 확장 API와 기존 `/ask` 연결 |
| `backend/docker/postgres-init/` | 신규 설치용 스키마; 기존 DB에는 별도 마이그레이션 제공 |
| `backend/eval/` | 기능별 데이터·baseline 비교·집계 보고서 |
| `backend/tests/` | 단위·API·인프라 통합·시나리오 테스트 |
| `frontend/src/` | 업로드·OCR 확인·요약·출처·오류 상태 UI |

제안 API:

| 경로 | 용도 |
|---|---|
| 기존 `POST /ask` 확장 | 질문·문서 범위·응답 모드 전달, 추적 ID 반환 |
| `POST /documents` | 업로드 후 문서 ID·처리 상태 반환 |
| `GET /documents/{id}` | 추출 결과·페이지·처리 상태 조회 |
| `PATCH /documents/{id}/text` | OCR 결과 수정 및 후속 색인 갱신 |
| `POST /documents/{id}/summary` | 출처가 포함된 요약 생성 |
| `DELETE /documents/{id}` | 원본·추출 결과·색인 정리 |
| `GET /admin/metrics` | 접근이 제한된 오류·시간·사용량 집계 |

문서 업로드 후 추출·검증·색인 완료 상태를 명확히 구분한다. 긴 처리는 작업 ID와 상태 조회 방식으로 제공하고, 처리 중 문서를 검색하지 않는다.

## 7. 테스트·문서·변경 이력

### 7.1 테스트 계층

- 단위: 추출 스키마, 필수값, OCR 후처리, 도구 인자 검사, 인용 ID, 재시도 상한, 토큰 집계.
- API: 실제 HTTP 요청으로 입력 검증·업로드·응답 상태·오류 계약 확인. 모델과 도구는 대역을 사용한다.
- 그래프: 성공·질의 재작성·재생성·호출 상한·타임아웃·캐시 hit 경로를 실제 compiled graph로 실행한다.
- 인프라 통합: 격리된 Qdrant/PostgreSQL에서 색인·검색·캐시·사용량 저장을 확인한다. 운영 컬렉션을 사용하지 않는다.
- 외부 모델 smoke: 명시적으로 실행하는 소규모 실제 LLM 테스트로 구조화 응답과 Tool Calling을 검증한다. 비용이 드는 테스트는 기본 오프라인 테스트와 분리한다.
- E2E: XML 질문, 조문 조회, 문서 요약, 이미지 OCR, 범위 밖 질문 시나리오를 확인한다.

기존 API 테스트는 경로·스키마 중심이므로 전체 요청 성공을 입증하는 테스트를 별도로 추가해야 한다.

### 7.2 문서 산출물

- `README.md`: 기능·구조·설치·기본 실행·테스트 명령 최신화.
- `docs/API_GUIDE.md`: 요청·정상/보류/실패 응답·업로드 예제.
- `docs/RUNBOOK.md`: 환경변수, 모델/OCR 설정, DB 마이그레이션, 장애 확인, 재현 절차.
- `docs/EVALUATION_REPORT.md`: baseline과 변경 후 지표·실패 사례·비용 및 지연 비교.
- `CHANGELOG.md`: 버전별 추가·변경·수정·호환성·마이그레이션 안내.
- 기존 `docs/TRIALS_AND_ERRORS.md`: 원인·해결·재발 방지 기록 유지.

## 8. 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 그래프 실행 정비·중복 검색 제거·baseline 고정 | `/ask`가 compiled graph를 실행하고 경로별 테스트 통과 |
| 2 | 구조화 추출·LLM 분류·Tool Calling | 도구 선택부터 실행 결과를 이용한 답변까지 재현 |
| 3 | JSON·인용·근거 검증·누락·재시도 | 잘못된 응답의 수정 또는 명시적 보류, 호출 상한 검증 |
| 4 | PDF·이미지·OCR·요약·UI | 업로드→확인→요약→근거 조회 시나리오 완료 |
| 5 | 사용량·오류·시간 기록·비교 평가 | 요청 단위 추적과 동일 조건 전후 보고서 생성 |
| 6 | 통합 테스트·실행 가이드·변경 이력 | 격리된 환경에서 가이드만으로 서비스·테스트 재현 |

사용량 수집은 2단계부터 연결하고 5단계에서 집계·보고서를 완성한다. 테스트는 각 단계와 함께 작성한다. OCR·PDF·구조화 출력 관련 라이브러리와 모델은 실제 구현 시 최신 공식 문서·한국어 지원·제공자 호환성을 확인해 선정한다.

전체 완료 조건:

1. LLM 기반 추출·분류·요약·생성을 각각 API와 평가 결과로 입증한다.
2. 텍스트 문서와 스캔 이미지 입력을 모두 처리하고 원문 위치를 추적한다.
3. LLM이 선택한 도구의 이름·인자·실행 결과·후속 답변이 연결된다.
4. 형식 오류·누락·근거 부족·일시 오류에 대해 제한된 복구와 최종 상태를 제공한다.
5. baseline과 확장 버전을 품질·오류·시간·사용량으로 비교한다.
6. 단위·API·실제 인프라 통합 테스트와 문서가 함께 제공된다.
7. 현재 알려진 제한사항을 보고서에 명시하고 미측정 개선 효과를 성과로 기재하지 않는다.

## 9. 구현 완료 후 포트폴리오 표현 예시

> LLM 기반 법령 정보 추출·의도 분류·문서 요약·답변 생성 기능을 구현했다. XML·PDF·스캔 이미지의 텍스트를 구조화하고 Hybrid RAG와 Tool Calling을 연동했으며, 응답 스키마·인용·근거 검증과 누락·재시도 처리를 적용했다. 평가 데이터로 변경 전후 품질·오류·응답 시간·모델 사용량을 비교하고, 단위·통합 테스트와 API 문서·실행 가이드·변경 이력을 관리했다.

위 문장은 모든 완료 기준을 충족한 뒤 사용한다. 수치 성과는 실제 측정값과 평가 조건을 함께 적는다.
