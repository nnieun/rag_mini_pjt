# AI 기본법 RAG 프로젝트 시행착오 기록

이 문서는 AI 기본법 RAG 프로젝트를 진행하면서 발생한 오류와 잘못된 접근, 원인, 해결 방법, 최종 판단을 시간 순서로 정리한다. 단순한 성공 결과보다 **왜 기존 방법을 바꿨는지**를 재현할 수 있도록 기록했다.

## 1. 법령 Open API 검색 결과가 0건이었던 문제

### 증상

```text
검색어: 인공지능 / 전체 검색 결과: 0건
```

`lawSearch`를 호출했지만 검색 결과가 없었다.

### 확인한 내용

- 국가법령정보센터 웹 검색에서는 동일한 검색어로 결과가 존재했다.
- Open API는 웹 검색 URL과 별도 요청 규칙을 사용한다.
- `OC`, `target`, `type`, `query`가 API 규격에 맞아야 한다.

### 해결

`.env`에 국가법령정보센터 Open API의 사용자 식별값을 저장했다.

```dotenv
LAW_API_OC=발급받은_OC
```

검색 요청에는 다음 값을 사용했다.

```python
{
    "OC": LAW_API_OC,
    "target": "law",
    "type": "XML",
    "query": "인공지능",
}
```

### 결과

검색 결과 23건을 확인했고, 시행일이 2026년 7월 21일인 AI 기본법을 선택했다.

```text
인공지능 발전과 신뢰 기반 조성 등에 관한 기본법
시행일: 20260721
MST: 282791
```

### 교훈

웹사이트 검색 결과와 Open API 결과는 자동으로 같아지지 않는다. API 인증값과 API 전용 파라미터를 먼저 검증해야 한다.

## 2. 검색 결과에서 어떤 법령을 선택해야 하는지 혼란

### 증상

같은 법령명이 여러 번 검색됐다.

```text
제16번: 시행일 20260721, MST=282791
제17번: 시행일 20260122, MST=282791
제18번: 시행일 20260122, MST=276241
제19번: 시행일 20260122, MST=268543
```

### 원인

법령명만 비교하면 현행·예정·이전 법령을 구분할 수 없었다.

### 해결

프로젝트에서 요구한 시행일과 공포일을 함께 비교했다.

```text
시행일: 2026. 7. 21.
공포일: 2026. 1. 20.
법률 제21311호
MST: 282791
```

### 교훈

법령 선택 기준에는 법령명뿐 아니라 시행일, 공포일, 공포번호, MST를 포함해야 한다.

## 3. 상세 조회 XML ParseError

### 증상

```text
ParseError: mismatched tag: line 15, column 2
```

XML이라고 생각한 응답을 `ElementTree.fromstring()`으로 파싱했지만 실패했다.

### 원인

API가 정상 법령 XML이 아닌 오류 페이지 또는 비정상 응답을 반환했는데 바로 XML로 파싱했다.

### 해결

파싱 전에 다음을 확인하도록 변경했다.

- HTTP 상태 코드
- `Content-Type`
- 응답 앞부분
- XML 최상위 태그
- 오류 메시지 포함 여부

### 교훈

외부 API 응답은 곧바로 파싱하지 말고 정상 응답인지 먼저 검사해야 한다. XML 파싱 오류는 XML 코드보다 요청 파라미터 오류일 가능성이 높다.

## 4. 상세 응답의 태그가 `Law` 하나뿐이었던 문제

### 증상

```python
tags = sorted({element.tag for element in detail_xml.iter()})
print(tags)
```

```text
['Law']
```

응답 내용:

```xml
<Law>일치하는 법령이 없습니다. 법령명을 확인하여 주십시오.</Law>
```

### 원인

상세 조회 파라미터가 API가 기대하는 형식과 맞지 않아 오류 XML을 정상 XML로 오해했다.

### 해결

목록 조회에서 얻은 법령 일련번호를 상세 조회의 `ID`에 전달했다.

```python
detail_params = {
    "OC": OC,
    "target": "eflaw",
    "type": "XML",
    "ID": selected["law_id"],
}
```

### 정상 결과

```text
최상위 태그: 법령
```

하위에서 다음 태그를 확인했다.

```text
기본정보, 조문, 조문단위, 항, 호, 목, 부칙, 제개정이유
```

### 교훈

XML 파싱 성공과 API 요청 성공은 다르다. 오류 메시지도 유효한 XML일 수 있으므로 최상위 태그와 본문을 검사해야 한다.

## 5. 조문 데이터가 0개였던 문제

### 증상

```text
조문 데이터 0개를 만들었습니다.
```

### 원인

파서의 XPath 문제가 아니라 입력 XML이 실제 법령 XML이 아니었다. `<Law>` 오류 응답에는 `조문단위`가 존재하지 않았다.

### 해결

상세 조회 요청을 바로잡아 최상위 태그가 `법령`인 전체 XML을 받은 후 다음 경로를 사용했다.

```python
root.findall("./조문/조문단위")
```

### 교훈

파싱 결과가 0개라면 XPath만 수정하지 말고 원본 응답 자체를 먼저 확인해야 한다.

## 6. 조문만 가져오면 되는지에 대한 혼란

### 초기 접근

검색을 위해 `조문내용`, `항내용`, `호내용`, `목내용`만 추출했다.

### 문제

법령 XML에는 조문 외에도 중요한 정보가 있다.

- 기본정보
- 장·절 구조
- 부칙
- 제·개정이유
- 공포일과 시행일
- 조문별 시행일

### 최종 판단

원본 XML은 전체를 그대로 저장하고, 검색 청크를 만들 때만 필요한 구조를 선택적으로 사용한다.

```text
원본 보존: 전체 XML
검색 단위: 조·항·호·목 기반 청크
metadata: 기본정보·장·절·시행 정보
별도 자료형: 부칙·제개정이유
```

### 교훈

Loading과 Chunking은 별개다. 원본은 손실 없이 보존하고 검색 목적에 맞게 파생 데이터를 만들어야 한다.

## 7. XML 파일 경로 오류

### 증상

```text
FileNotFoundError: .../data/ai_basic_law/ai_basic_law.xml
```

### 원인

- Notebook 실행 위치가 프로젝트 루트인지 `notebook/`인지 달랐다.
- 파일명 문자열에 불필요한 역슬래시가 들어갔다.

```text
ai_basic_law\.xml
```

이 경우 의도한 `ai_basic_law.xml`과 다른 파일명이 된다.

### 해결

프로젝트 루트를 탐색한 뒤 `pathlib.Path`로 경로를 만들었다.

```python
PROJECT_ROOT = next(
    path
    for path in [Path.cwd(), *Path.cwd().parents]
    if (path / "common" / "ai_model.py").exists()
)

XML_PATH = (
    PROJECT_ROOT
    / "data"
    / "ai_basic_law"
    / "ai_basic_law.xml"
)
```

### 교훈

Notebook의 현재 디렉터리를 고정값으로 가정하지 않는다. 파일 경로에는 정규식용 escape를 사용하지 않는다.

## 8. Qdrant에 다시 저장하면 어떻게 되는지에 대한 혼란

### 확인 사항

같은 컬렉션에 같은 point ID를 `upsert`하면 해당 point는 갱신된다. 하지만 이전 실험의 다른 point가 자동으로 모두 삭제되는 것은 아니다.

### 최종 방식

청킹 실험마다 컬렉션 이름을 다르게 사용했다.

```text

ai_basic_law_adaptive_anchor_v1
```

최종 청킹 Notebook은 자신이 사용하는 컬렉션만 삭제 후 재생성한다.

### 교훈

실험 비교 시 같은 컬렉션에 덮어쓰지 말고 버전별 컬렉션을 분리해야 한다.

## 9. `embedding_client` NameError

### 증상

```text
NameError: name 'embedding_client' is not defined
```

### 원인

Notebook 커널을 재시작하거나 셀 실행 순서가 바뀌면서 초기화 셀을 실행하지 않았다.

### 해결

검색 전에 다음 셀을 실행한다.

```python
embedding_client = get_embedding_model()
qdrant_client = get_qdrant_client()
```

### 교훈

Notebook은 파일 위에서 아래로 실행된다는 보장이 없다. 설정·클라이언트 초기화 셀을 명확하게 분리하고 커널 재시작 후 전체 실행으로 검증해야 한다.

## 10. 초기 54개 조문 청킹의 문제

### 결과

```text
문서 수: 54개
```

검색 결과에 다음과 같은 청크가 포함됐다.

```text
제1절 인공지능산업 기반 조성
제2절 인공지능기술 개발 및 인공지능산업 활성화
```

### 문제

- 장·절 제목이 조문처럼 저장됐다.
- 내용이 짧은 제목 청크가 검색 결과를 차지했다.
- 긴 조문은 세부 개념 검색 정밀도가 낮았다.

### 해결

`조문여부 == "전문"`인 장·절 제목은 독립 검색 청크에서 제외하고 metadata로만 보존했다.

### 교훈

법률 XML의 `조문단위`가 모두 실제 조문인 것은 아니다.

## 11. 조 단위 청킹에서 정의 조문이 밀린 문제

### 질문

```text
고영향 인공지능이란 무엇인가요?
```

### 초기 결과

제33조 확인, 제31조 투명성 의무, 제35조 영향평가가 검색됐지만 정의가 있는 제2조는 상위에 나오지 않았다.

### 원인

제2조 하나에 12개 정의와 여러 목이 들어 있어 Embedding이 특정 정의를 충분히 대표하지 못했다.

### 해결 방향

긴 조문을 항·호·목까지 구조적으로 나누는 실험을 시작했다.

### 교훈

법률에서 “정의” 조문은 조 하나가 매우 길 수 있으므로 조 단위만으로는 부족하다.

## 12. 조 + 항 청킹의 번호 중복

### 증상

```text
① ① 인공지능사업자는 ...
1. 1. 위험관리방안의 수립·운영
```

### 원인

XML의 `항내용`, `호내용`, `목내용`에 이미 번호가 포함되어 있는데 파서가 번호를 다시 앞에 붙였다.

### 해결

- `content`에는 XML 원문을 그대로 사용한다.
- 항·호·목 번호는 metadata와 위치 표시에만 사용한다.

### 교훈

표시용 번호와 본문에 포함된 번호를 분리해야 한다.

## 13. 조 + 항만으로 제2조를 해결하지 못한 문제

### 결과

제2조는 구조상 하나의 항 아래에 12개의 호가 있는 형태였다. 항 단위로 나누어도 고영향 인공지능, 생성형 인공지능, 인공지능사업자 등의 정의가 한 청크에 남았다.

### 해결

정의 조문은 호 단위까지 내려가도록 했다.

### 교훈

고정된 “조 + 항” 전략보다 실제 XML 트리 깊이에 따라 내려가는 적응형 전략이 필요하다.

## 14. 모든 조·항·호·목을 저장해 400개 이상이 된 문제

### 시도

검색 정밀도를 높이기 위해 모든 계층을 독립 청크로 저장했다.

### 결과

약 400개 이상의 청크가 생성됐다.

### 문제

- 같은 내용이 조·항·호·목에 반복됐다.
- 제34조의 여러 호가 Top-K를 점유했다.
- 세부 청크 수는 늘었지만 검색 결과 다양성이 낮아졌다.

### 판단

청크 수 자체보다 **동일 근거의 중복 검색**이 핵심 문제였다.

### 교훈

법률 계층을 모두 이해해야 하지만 모든 계층을 동시에 검색 대상으로 만들 필요는 없다.

## 15. 선택적 계층 청킹 약 229개의 한계

### 시도

- 모든 조
- 직접 `항내용`이 있는 항
- 항 본문이 없고 호 목록만 있는 경우의 호

위 단위만 저장했다.

### 개선

전체 계층 방식보다 청크 수와 중복이 줄었다.

### 한계

직접 항 내용이 있는 항의 개별 호가 검색에서 빠질 수 있었다. 제34조처럼 항 도입 문장과 여러 구체적 의무를 모두 검색해야 하는 조문에는 충분하지 않았다.

### 교훈

“항 내용이 있는가”만으로 하위 호 저장 여부를 결정하면 세부 근거를 놓칠 수 있다.

## 16. `split.py` 검토에서 발견한 문제와 개선

### 장점

`split.py`는 고정 계층 청킹이 아니라 다음 적응형 방식을 사용했다.

- 짧은 조문은 유지
- 긴 조문은 부모로 보존
- 항 → 호 → 목 순으로 필요한 깊이까지만 분할
- 너무 긴 leaf만 문자 길이로 보조 분할
- 장·절을 metadata로 보존
- 부칙·제개정이유 별도 처리

### 실행 문제

현재 환경에서 다음 문제가 있었다.

```text
ModuleNotFoundError: langchain_text_splitters
```

또한 `split.py`가 `common.config.SERVICE`를 가져오지만 현재 설정에는 `SERVICE`가 없었다.

### 추가로 발견한 검색 문제

제2조제4호 전체가 길면 바로 가~카목으로 내려가 정의 도입 문장 자체가 독립 검색 결과로 남지 않았다. 각 목에 정의 문장을 반복하면 Top-K 중복이 생길 수 있었다.

### 해결

긴 항·호의 도입 문장을 `anchor`로 별도 저장했다.

```text
제2조제4호 anchor: 고영향 인공지능의 정의
제2조제4호가목~카목 child: 개별 적용 영역
```

### 교훈

Parent/Child 구조만으로 부족할 수 있으며 목록 도입부를 대표하는 Anchor가 필요하다.

## 18. Embedding API Rate Limit

### 증상

```text
RateLimitError: 429
MonoRouter: Rate limit exceeded (30 requests per minute)
```

### 원인

- 여러 질문을 반복 임베딩했다.
- Dense와 Hybrid가 같은 질문 Embedding을 각각 요청했다.
- 대량 문서 임베딩 중 내부 배치 하나가 실패하면 전체를 다시 실행했다.

### 단계별 해결

1. 질문별 Embedding 캐시를 추가했다.
2. Golden Set 질문을 배치로 미리 임베딩했다.
3. 429 발생 시 65초 후 재시도했다.
4. 문서 임베딩을 20개 단위로 나눴다.
5. 성공한 배치는 유지하고 실패한 현재 배치만 다시 요청했다.

### 교훈

재시도만 추가하면 이미 성공한 요청까지 반복할 수 있다. 캐시와 작은 배치를 함께 사용해야 한다.

## 19. 무한 재시도의 위험

### 요구

Notebook 실험이 429로 중단되지 않도록 무한 재시도를 적용했다.

### 보완

모든 예외를 무한 재시도하면 코드 오류도 영원히 반복된다. 다음 경우만 재시도하도록 제한했다.

```text
429
rate limit
rate_limit
```

FastAPI에서는 요청이 무한히 대기하지 않도록 기본 최대 3회 재시도로 변경했다.

### 교훈

Notebook의 장시간 실험과 운영 API의 실패 정책은 달라야 한다.

## 22. Reranking이 항상 좋아지는 것은 아니었던 문제

### 단일 질문 결과

“고영향 인공지능이란 무엇인가요?”에서 정답 제2조가 다음처럼 개선됐다.

```text
Hybrid: 2위, MRR=0.5
Hybrid+Reranking: 1위, MRR=1.0
```

### 전체 결과

Reranking은 MRR을 크게 높였지만 Hit@5와 Recall@5는 Hybrid보다 낮았다. 일부 정답 근거를 Top-5 밖으로 밀어냈다.

### 최종 판단

프로젝트 기준은 Hit@5와 Recall@5를 우선하므로 최종 Retrieval 방법은 Hybrid(C)로 결정했다.

### 교훈

Reranking은 순위를 개선할 수 있지만 검색 커버리지를 해칠 수도 있다. Hit, Recall, MRR을 함께 봐야 한다.

## 30. 가장 중요한 교훈

1. XML 파싱 오류보다 먼저 API 응답 자체가 정상인지 확인한다.
2. 원본 Loading과 검색용 Chunking을 분리한다.
3. 법률 문서는 글자 수보다 조·항·호·목 구조를 우선한다.
4. 세밀하게 많이 나누는 것보다 중복 없이 필요한 단위를 검색하는 것이 중요하다.
5. 긴 목록의 도입 문장은 Anchor로 보존한다.
6. 검색 청크와 답변 Context를 분리하고 Parent Retrieval을 사용한다.
7. Rate Limit은 캐시, 배치, 재시도를 함께 적용한다.
8. 소수 질문의 좋은 결과를 전체 성능으로 일반화하지 않는다.
9. Hit·Recall·MRR을 함께 비교한다.
10. Retrieval 성능이 높아도 답변의 근거 충실성과 Hallucination을 별도로 평가한다.

## 31. 답은 맞았지만 정의 조항이 2위로 나온 문제

### 증상

화면에서 `고영향 인공지능이란 무엇인가요?`라고 질문했을 때 답변 자체는 맞았다. 그런데 근거 목록을 살펴보니 정작 정의가 적힌 제2조가 아니라 제33조가 먼저 나오고 있었다.

```text
질문: 고영향 인공지능이란 무엇인가요?

1위: 제33조 고영향 인공지능의 확인
2위: 제2조 정의
```

LLM이 2위에 있던 제2조를 잘 골라서 답했기 때문에 겉으로는 문제가 없어 보였다. 하지만 검색 품질만 보면 정답이 2위이므로 MRR은 `0.5`다. 지금은 LLM이 잘 골랐지만, 비슷한 상황에서 항상 그럴 것이라고 기대할 수는 없어서 검색 순위도 바로잡을 필요가 있었다.

### 원인

원인은 비교적 단순했다. 질문과 제33조에 `고영향 인공지능`이라는 말이 여러 번 나오기 때문에 Dense와 BM25 모두 제33조를 관련성이 높은 문서로 본 것이다. 현재 Hybrid 검색의 RRF는 여러 검색 결과의 순위를 합칠 뿐, 해당 조문이 정의를 설명하는지 확인 절차를 설명하는지까지 판단하지는 않는다.

### 어떤 방법이 나은지 직접 비교해 보기

처음에는 정의형 질문에 metadata 가중치를 주는 방법과 Qwen으로 다시 순위를 매기는 방법 중 어느 쪽이 나을지 고민했다. 추측으로 고르지 않고, 둘을 결합한 경우까지 포함해 같은 Golden Set 45문항으로 비교했다.

1. `Hybrid`: Dense + BM25 + RRF 기준선
2. `Hybrid+DefinitionMetadata`: 정의형 질문에 정의 제목, 정의문 표현, Anchor metadata 가중치 적용
3. `Hybrid+ConditionalRerank`: 정의형 질문에만 Qwen Reranker 적용
4. `Hybrid+Metadata+ConditionalRerank`: metadata 순위와 Qwen 순위를 다시 RRF로 결합

Qwen을 모든 질문에 적용하면 느려지기 때문에, 질문 문장만 보고 정의형인지 먼저 판단했다.

```text
긍정 표현: 이란, 정의, 뜻, 의미, 누구를 말, 무엇인가, 어떤 사람
제외 표현: 확인 절차, 해당 여부, 평가 방법, 평가 항목, 의무, 과태료, 처벌
```

평가 데이터에 이미 들어 있는 `type` 값은 결과를 나눠 볼 때만 사용했다. 실제 검색에서 정답 label을 미리 보는 일이 없도록 정의형 판별에는 질문 텍스트만 사용했다.

### 평가 결과

전체 45문항 결과:

| 방법 | Hit@5 | Recall@5 | MRR@5 | 평균 시간 |
|---|---:|---:|---:|---:|
| Hybrid | 0.928571 | 0.892857 | 0.721032 | 8.14ms |
| Hybrid+DefinitionMetadata | 0.904762 | 0.869048 | 0.696032 | 8.15ms |
| Hybrid+ConditionalRerank | **0.928571** | **0.892857** | **0.750794** | 596.61ms |
| Hybrid+Metadata+ConditionalRerank | 0.928571 | 0.892857 | 0.726984 | 596.62ms |

정의형 5문항 결과:

| 방법 | Hit@5 | Recall@5 | MRR@5 | 평균 시간 |
|---|---:|---:|---:|---:|
| Hybrid | 1.0 | 1.0 | 0.9 | 21.37ms |
| Hybrid+DefinitionMetadata | 0.8 | 0.8 | 0.8 | 21.43ms |
| Hybrid+ConditionalRerank | **1.0** | **1.0** | **1.0** | 4,935.12ms |
| Hybrid+Metadata+ConditionalRerank | 1.0 | 1.0 | 0.9 | 4,935.19ms |

### 빠른 metadata 가중치가 오히려 점수를 떨어뜨렸다

처음 질문만 보면 metadata 방식도 성공한 것처럼 보였다. 제2조가 바로 1위로 올라왔기 때문이다. 하지만 다른 정의 질문에서 문제가 생겼다.

```text
질문: 인공지능취약계층이란 어떤 사람들인가요?
정답: 제3조
```

`인공지능취약계층`에 대한 근거는 제3조에 있는데, metadata 가중치는 제목이 `정의`인 제2조를 너무 강하게 밀어 올렸다. 결국 상위 5개가 제2조의 여러 하위 청크로 채워지고 정답인 제3조가 빠졌다.

```text
Hybrid: 제3조 1위, Hit@5=1, MRR@5=1
Metadata: 제2조 청크 편중, Hit@5=0, MRR@5=0
```

여기서 모든 용어의 정의가 꼭 제2조에 있는 것은 아니라는 점을 놓치고 있었다. `정의 질문이면 제2조를 우대한다`는 규칙은 한 질문에는 잘 맞았지만 다른 질문을 망가뜨렸다. 같은 조문의 하위 청크가 Top-K를 차지하는 중복 문제도 같이 드러났다.

### 조건부 리랭킹은 순위만 개선했다

반면 Qwen 리랭커를 정의형 질문에만 적용하자 제2조가 1위로 올라왔다.

```text
고영향 인공지능 정의 질문
Hybrid: 제33조 → 제2조, MRR@5=0.5
조건부 리랭킹: 제2조 → 제35조 → 제33조, MRR@5=1.0
```

무엇보다 기존 Hybrid의 Hit@5와 Recall@5는 그대로 유지하면서, 전체 MRR@5가 `0.721032`에서 `0.750794`로 올랐다. 정의형 5문항만 보면 MRR@5가 `0.9`에서 `1.0`이 됐다. 다섯 질문 모두 정답 조문이 첫 번째로 나온 것이다.

물론 공짜로 얻은 개선은 아니다. 현재 CPU에서 Qwen 리랭커를 실행하면 정의형 질문 하나에 평균 약 `4.9초`가 걸렸다. 다만 정의형 질문에만 실행했기 때문에 전체 45문항 기준 평균은 약 `0.60초`였다.

### 최종 판단

```text
일반 질문 → Hybrid(Dense + BM25 + RRF)
정의형 질문 → Hybrid 후보 검색 → Qwen Reranking
```

결론적으로 metadata 가중치는 사용하지 않기로 했다. 빠르다는 장점은 있지만 일부 정의를 제2조로 잘못 몰아주는 문제가 더 컸고, Qwen과 결합해도 결과가 더 좋아지지 않았다.

지금 결과만 놓고 보면 일반 질문은 기존 Hybrid로 검색하고, 정의형 질문으로 판단될 때만 Qwen으로 순위를 다시 매기는 방법이 가장 낫다. 기존에 찾던 정답을 잃지 않으면서 정의 조항을 1위로 올렸기 때문이다.

비교가 끝난 뒤 FastAPI에도 이 흐름을 연결했다. 이제 기본값으로 정의형 질문만 Qwen 리랭킹을 거치며, 일반 질문은 기존 Hybrid 검색 결과를 그대로 사용한다. 필요하면 `.env`에서 `RAG_CONDITIONAL_RERANK=false`로 꺼둘 수 있다.

### 관련 결과 파일

```text
backend/eval/compare_definition_strategies.py
backend/eval/results/definition_strategy_overall.csv
backend/eval/results/definition_strategy_definition.csv
backend/eval/results/definition_strategy_detail.csv
```

### 이번에 배운 점

1. 답변이 맞는 것과 검색 순위가 좋은 것은 별개의 문제였다.
2. 법률에서 용어 정의가 항상 `정의` 조문에만 있는 것은 아니다.
3. 간단한 가중치는 빠르지만, 잘못 정한 규칙 하나가 검색 결과 전체를 밀어낼 수 있다.
4. 느린 리랭커는 모든 질문에 쓰기보다 효과가 확인된 질문에만 쓰는 편이 현실적이다.
5. 두 방법을 합친다고 항상 더 좋아지는 것은 아니었다. 결국 같은 평가 데이터로 확인해야 했다.

## 32. 같은 질문을 다시 열 때 토큰이 다시 사용된 문제

처음에는 최근 질문을 다시 누를 때마다 `/ask`를 새로 호출했다. 질문 임베딩은 백엔드 메모리에 남아 있었지만, Qdrant 검색과 조건부 리랭킹, LLM 답변 생성은 다시 실행됐다. 특히 LLM 답변 생성 토큰을 계속 사용한다는 점이 아쉬웠다.

우선 프론트에서는 한 번 받은 `AskResponse`를 질문별로 메모리에 보관했다. 그래서 같은 브라우저 세션 안에서는 최근 질문을 다시 눌러도 API를 호출하지 않는다. 다만 새로고침하면 이 값은 사라진다.

새로고침하거나 다른 브라우저에서 같은 질문을 해도 재사용할 수 있도록 PostgreSQL에 `answer_cache` 테이블을 추가했다. 흐름은 다음과 같다.

```text
브라우저 메모리 캐시
→ 없으면 PostgreSQL 답변 캐시
→ 없으면 Hybrid 검색·조건부 리랭킹·LLM 답변 생성
```

캐시 키를 질문만으로 만들지는 않았다. 정규화한 질문, Qdrant 컬렉션명, 파이프라인 버전을 함께 SHA-256으로 해시했다. 법령 데이터나 검색 전략이 달라졌는데 예전 답변이 그대로 나오는 일을 피하기 위해서다.

```dotenv
RAG_ANSWER_CACHE_ENABLED=true
RAG_CACHE_TTL_DAYS=30
RAG_CACHE_VERSION=conditional-rerank-v1
```

법령 원문, 청킹 방식, 프롬프트 또는 검색 전략을 바꾸면 `RAG_CACHE_VERSION`을 올려 이전 캐시를 무효화한다. 캐시가 적중하면 API 응답의 `cache_hit`이 `true`가 되고, 검색·리랭킹·LLM 호출을 모두 생략한다.

PostgreSQL이 잠시 꺼져 있거나 인증에 실패하더라도 QA API 전체가 시작되지 않는 문제는 피하고 싶었다. 그래서 앱 시작 시 5초 동안 캐시 DB 연결을 시도하고, 실패하면 경고를 남긴 뒤 캐시 없이 서비스를 계속 실행하도록 했다.

캐시를 붙인 뒤 검색 로직을 수정했는데도 예전 답변이 계속 보이는 문제도 생겼다. 이를 해결하기 위해 검색 전략 변경 시 캐시 버전을 올리고, API 요청의 `refresh=true`와 화면의 `다시 검색` 버튼을 추가했다. `다시 검색`을 누르면 브라우저 캐시와 PostgreSQL 조회를 모두 건너뛰어 새로 검색하고, 새 답변으로 기존 캐시를 덮어쓴다.

캐시 응답은 빠르기 때문에 화면의 실행 시간이 `0.0초`로 바뀌면서 원래 검색에 얼마나 걸렸는지 알 수 없는 문제도 있었다. 현재 요청 시간인 `elapsed_ms`와 최초 답변 생성 시간인 `processing_ms`를 따로 저장하도록 바꿨다. 캐시에서 불러온 답변은 `기존 검색 4.9초 · 캐시 조회 0.0초`처럼 두 시간을 함께 표시한다.
